# CLAUDE.md

Repo-level guidance for Claude Code / automation-pipeline agents working in this repository.

## Automation Pipeline Learnings

- **[NON-NEGOTIABLE] When a skill or agent actually runs a testcase (`npx playwright test ...`), never run it inside the default command sandbox — run it with the sandbox override from the start.** The sandboxed shell's filesystem and network restrictions produce failures that look like real test/app failures but aren't: a Chromium `ProcessSingleton`/profile "Operation not permitted" error (browser can't launch/write its profile dir) and a DNS `getaddrinfo ENOTFOUND <host>` error (network calls to hosts outside the sandbox's allowlist, e.g. anything but `registry.npmjs.org`, are blocked outright). Both were hit and had to be re-run outside the sandbox to get a real pass/fail signal (see the `@homepage-heading-and-get-started-link` UI run and the `@api-fetch-user-by-id`/`@api-create-user` API runs). Don't try sandboxed first and fall back on failure — that wastes a run and risks a sandbox artifact being misread as evidence. Any test execution (via `debug-a-testcase` or any other skill/agent step that runs Playwright tests) should go straight to the sandbox override.
- **Check installed tool versions before trusting a plan's example config values.** During the initial framework scaffold, three separate version-skew issues surfaced (ESLint config format, TypeScript `moduleResolution` deprecation, and a Jenkinsfile Docker image tag pinned to an older Playwright version than what's actually installed/locked). Before finalizing any config file that pins or assumes a tool version (Docker image tags, `moduleResolution`, ESLint config format, etc.), cross-check against the actually-installed version in `package.json`/the lockfile rather than copying a plan's example verbatim.
- **This repo's ESLint (9+, currently 10.x) only supports flat config.** Use `eslint.config.mjs`, not `.eslintrc.cjs`/`.eslintrc.json` — the legacy format was removed in ESLint 9. Any future plan that specifies a legacy `.eslintrc.*` file name should be implemented as flat config instead.
- **`npm init playwright@latest`'s `--gha` flag is presence-only (boolean).** There is no `--gha=false` form — to skip generating a GitHub Actions workflow (e.g. when the CI target is Jenkins/GitLab/Azure DevOps), simply omit the flag entirely rather than trying to pass a falsy value.
- **No Sonar server/token is configured in this repo yet.** `code-quality-agent`'s scan (SonarQube/SonarCloud/Sonar Scanner) will block on first run until an SDET supplies a server URL/org key and `SONAR_TOKEN` via an environment variable (never paste a token in chat). Until that's set up, treat a Sonar-gate skip as expected rather than a pipeline defect, and fall back to the ESLint + manual code-review gate as the quality signal.
- **When adding tests for a new target site/app, add a dedicated `<SITE>_BASE_URL` env var in `config/env.ts` instead of repointing the shared `BASE_URL`.** `playwright.config.ts`'s UI projects (`chromium`/`firefox`/`webkit`) share one `baseURL` across all specs, and other suites (e.g. `tests/ui/example.spec.ts`) already depend on the existing `BASE_URL` pointing at their own target. Introduced when adding the SauceDemo slice (`SAUCEDEMO_BASE_URL`) — follow the same pattern for any future third-party/demo site added to this repo rather than overwriting the shared var.
- **When building a navigation URL from a `<SITE>_BASE_URL`-style env var, don't raw-concatenate a path onto it (e.g. `` `${env.X_BASE_URL}inventory.html` ``).** That only works if the env value happens to already end in `/`, which the Zod schema (`z.string().url()`) doesn't enforce — flagged in SauceDemo review cycle 1. Follow the existing `authenticatedPage` fixture's safer join pattern (`` `${env.BASE_URL}/path` ``, explicit separator) or normalize the trailing slash before use.
- **A non-interactive agent session cannot produce a genuine `npx playwright codegen` recording.** Codegen's Inspector recorder only captures actions from a human physically clicking/typing in the spawned browser window; an agent driving the same browser via automation calls doesn't trigger the recorder. When exploration must happen without a human present, the accepted substitute (used for the SauceDemo slice) is: run a headed (`headless: false`), live, scripted Playwright run against the real target to verify every locator/attribute/error string by printing/asserting it before trusting it, then hand-author a codegen-style `docs/exploration/<feature-slug>-codegen.ts` file from that verified real output — with a comment block at the top disclosing this substitution and why. This still satisfies the "explore real pages headed before writing test code, never guess locators" rule; a silently fabricated or from-memory exploration artifact would not.
- **Running actual headed/live Playwright browser tests in this sandboxed shell can hit a Chromium `ProcessSingleton`/profile permission error that is a sandbox filesystem restriction, not a real test failure.** Symptoms are "Operation not permitted"/"Permission denied" errors tied to the browser's profile directory. Confirm it's sandbox-caused (not a genuine bug) before spending time debugging the test itself, then rerun with the sandbox override to get a real pass/fail signal.
- **A `getByRole('heading', { name: /regex/i })` locator with no `level` scoping is fragile against a page that grows more headings matching that regex over time** — especially on a third-party/external site outside this repo's control. `pages/example.page.ts`'s `heading` locator (matching the `playwright.dev` homepage's `/playwright/i`-named heading) started throwing a strict-mode violation once the live site added three `<h3>` feature-card headings ("Playwright Test"/"Playwright CLI"/"Playwright MCP") alongside the original `<h1>` hero heading — all matching the same loose regex. Fixed by adding `level: 1` to scope to the intended hero/heading-tier element, keeping the regex (not hardcoding today's exact copy) since text drift is a separate, already-documented risk. When writing a heading locator by accessible-name regex against any page (and especially a third-party one), scope by `level` (or another discriminating role option) up front rather than relying on the regex alone to stay unique.
- **Implementation/review verification steps that run `tsc --noEmit` and `eslint` should also run `npx prettier --check` on changed files — ESLint passing does not guarantee Prettier compliance.** Surfaced in the SauceDemo network-interception review (cycle 1): both touched lines in `login.spec.ts`/`cart.spec.ts` failed `prettier --check` (over the `.prettierrc` `printWidth`), and the issue turned out to be repo-wide/pre-existing (41 files fail `prettier --check` repo-wide) rather than introduced by that change — but the implementation summary's verification section never ran Prettier at all despite it being a declared quality gate in this repo. Add a Prettier check alongside typecheck/lint in any future implementation or review verification pass so gaps like this are caught (or at minimum knowingly reported) rather than silently missed.
- **SauceDemo (`saucedemo.com`) makes zero backend API calls for its actual business logic** — login credential checks, inventory listing, and cart state are all client-side/bundled in JS, confirmed via real headed/scripted live-run network-traffic capture (`docs/exploration/saucedemo-network-interception-codegen.ts`) across the login and add-to-cart flows, reproduced across two independent runs. The only real, deterministic backend traffic observed on those flows is a pair of third-party Backtrace.io analytics beacons (`events.backtrace.io/api/unique-events/submit` and `.../summed-events/submit`), fired together on login-page-load and again on add-to-cart, consistently returning HTTP 401 with a fixed JSON error body (no valid API key configured for that beacon on this demo site — expected, not a bug). A related `submit.backtrace.io/UNIVERSE/TOKEN/json` call was observed to fail at the network level intermittently and is not reliable enough to assert on. Any future network-interception/mocking/response-validation work targeting SauceDemo should target this Backtrace beacon pair (or note there's nothing else to intercept) rather than assuming the app has a mockable backend API — see `utils/network.ts`'s `assertBacktraceEventsBeaconPair` helper for the established pattern.
- **`@api-fetch-user-by-id` and `@api-create-user` (`tests/api/example.spec.ts`, "Users API") cannot pass in this environment as currently configured, and this is not a code defect.** Both go through the worker-scoped `authToken` fixture, which `POST`s to `${API_BASE_URL}/auth/login` before every API test (by design — see `docs/plans/framework-setup-plan.md` §6a, and both tests' own requirements docs list a successful login as an explicit acceptance criterion, not incidental plumbing). The locally configured `API_BASE_URL` (gitignored `.env`) is `https://jsonplaceholder.typicode.com` — a public fake/demo REST API that supports `/users` but has **no authentication layer at all**, so `/auth/login` genuinely 404s there (confirmed via a real, unsandboxed HTTP response, not a network artifact). This is an infrastructure/environment gap — the test file's own header comment already predicted it ("point it at a backend that implements `/auth/login` and the `/users` resource"). A self-healing run on either tag investigated and confirmed there is no legitimate code-level fix: the SauceDemo-style "give it a dedicated `<SITE>_BASE_URL`" precedent doesn't apply (no other spec shares `API_BASE_URL`, so there's no collision to resolve — just the same unresolved "what real backend?" question under a new name), and bypassing/mocking the auth fixture would mean silently dropping a documented precondition rather than fixing anything. Do not attempt to code-fix this again on a future run — it needs an SDET to point `API_BASE_URL` at a real backend implementing both `/auth/login` and `/users` (locally in `.env`, and via the Jenkins `credentials('qa-api-base-url')` binding in CI per `docs/plans/framework-setup-plan.md` §8) before either test can be expected to pass.

## UI Automation Workflow

- **[TEMPERATURE 0 — NON-NEGOTIABLE]** Never write UI automation code before exploring the required pages with the Playwright CLI in headed mode. This is a strict, zero-deviation rule — not a preference to weigh against convenience, time pressure, or the apparent simplicity of the scenario. No exceptions.
- **Explore pages with the Playwright CLI before writing any test code.** When asked to automate a UI scenario, use the Playwright CLI (e.g. `npx playwright codegen`, or manual navigation/inspection of the target pages) to explore the real pages first, and only write automation code once that exploration gives full clarity on the flow, locators, and states involved. Do not write code first and then explore/modify test cases afterward to fix it — that ordering produces rework and was explicitly rejected.
- **Any browser opened for exploration must run headed (non-headless), never headless.** Whenever a step opens a browser to explore pages — `npx playwright codegen <url>`, ad-hoc scripts, or debug runs — run it in headed/headed mode so the browser window is actually visible, not with `--headless`/`headless: true`. This applies to exploration only; the checked-in `playwright.config.ts` for actual CI/test-suite execution is unaffected by this rule.
- **Exploration must standardize on `npx playwright codegen --output <path>`, not throwaway scripts, so raw generated code is actually saved and reviewable.** Ad-hoc headed scripts (e.g. a one-off `chromium.launch({ headless: false })` script) get discarded, leaving only a prose summary of what was found — locators and behavior end up asserted secondhand in a doc instead of verifiable against real generated output. Instead, run `npx playwright codegen --output docs/exploration/<feature-slug>-codegen.ts <url>` (adding `--save-storage docs/exploration/<feature-slug>-storage-state.json` when the flow requires being logged in for a later step) so the raw codegen output is committed under `docs/exploration/` alongside the requirements/plan/summary docs for that feature. This generated file is a reference artifact for locators/flow, not finished test code — it still gets refactored into page objects and specs per the framework's patterns, but reviewers can now diff what was actually observed against what got implemented.

## Test Tagging

- **Every testcase must carry tags, added or updated whenever a testcase is created or modified.** Use Playwright's `tag` test option (the options object passed as the second argument to `test()`, e.g. `test('logs in with valid credentials and lands on the inventory page', { tag: ['@smoke', '@login-valid-credentials'] }, async ({ page }) => { ... })`), not inline `@tag` text appended to the title string. Tag values still start with `@` per Playwright's convention. Consistent with existing specs like `tests/ui/saucedemo/login.spec.ts`.
- **Every testcase must have its own unique tag that identifies specifically what it tests**, in addition to any shared classification tags (`@smoke`, `@regression`, etc.), all listed in the same `tag` array. The unique tag should read as a short, kebab-case description of the scenario under test (e.g. `@login-valid-credentials`, `@login-invalid-password`, `@inventory-add-to-cart`), so a single tag alone is enough to identify which testcase ran/failed in a report without opening the file. Do not reuse a unique tag across two different testcases.
- When adding a new testcase or editing an existing one's behavior, review its tags as part of the change: add the unique scenario tag if missing, and add/update classification tags (`@smoke`, `@regression`, etc.) in the `tag` array to reflect what the test now covers.
